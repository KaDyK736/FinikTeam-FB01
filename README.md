# AI-помощник нового клиента Faberlic (кейс FB01)

**Команда:** Finik · **Репозиторий:** https://github.com/KaDyK736/FinikTeam-FB01

## 📌 Описание проекта
**Faberlic AI Assistant** — интеллектуальный помощник первичного контакта, который после учебного события регистрации самостоятельно проводит первый диалог с новым клиентом, выясняет его цель и интересы и передаёт наставнику заполненную карточку.  
Главный результат — понятный первый шаг для клиента и сохранённый контекст для наставника.  
Проект выполнен для кейс-чемпионата «ИИ-агенты для бизнеса» (23–25 сентября 2026), кейс FB01 «ИИ помощник нового клиента».

Схема работы: бот принимает сообщение, LLM-скрипт извлекает из свободного ответа структурированные сведения (цель, интересы, подтверждающую цитату), недополученный ответ возвращается на уточнение, итоговая карточка сохраняется в локальной БД и доступна наставнику.

## ⚙️ Установка и запуск
### План запуска
1. **Скопировать учебные данные** из `FB01_Faberlic_Новый_клиент/02_Учебные_данные` в `data/` (файлы вымышленные, реальные данные не используются).
2. **Запустить LLM-сервис** (один из вариантов, по убыванию предпочтения):
   - OpenRouter — зарегистрироваться, получить ключ, выбрать модель с пометкой **free**;
   - Mistral AI — если OpenRouter недоступен (требуется привязка номера);
   - Ollama — локальный запуск: `ollama pull llama3.1 && ollama serve`.
3. **Запустить backend бота** (Telegram, aiogram 3):
   ```bash
   cd bot
   pip install -r requirements.txt
   python main.py   # токен берётся из .env, в репозиторий не коммитится
   ```
4. **Инициализировать БД**: при первом старте создаётся локальная SQLite-база; тестовые пользователи (клиенты + наставники) заранее заносятся скриптом `seed_db.py` — заглушка вместо реальной интеграции с сайтом регистрации.
5. **Docker-вариант (основной для сдачи)**:
   ```bash
   docker compose up --build
   ```

### Сценарий проверки первым делом (с защиты)
1. **F002**: первичный диалог → цель «дополнительный доход» → карточка и следующий шаг.
2. **F004**: бот задаёт уточняющий вопрос вместо угадывания цели.
3. **F006**: остановка контакта по просьбе пользователя (`do_not_contact = true`).
4. Вопрос о несуществующей акции → передача обращения наставнику (без выдумывания условий).
5. Повторная загрузка события F001 → карточка **обновляется**, дубликат не создаётся.

## 🚀 MVP
- Загрузка учебного события регистрации с уникальным `client_id` и открытие диалога (без дублей при повторной загрузке).
- FSM-вопросы бота: цель, интересы, доступное время; повторный запрос уже известных сведений не задаётся.
- LLM-скрипт обработки ответа: извлечение цели, интересов и доступного времени в структурированный JSON, возврат «ответ неполный» при отсутствии обязательных полей; пользователь может редактировать свои ответы.
- Сегментация по 4 статусам цели (`personal` / `income` / `business` / `unknown`) только по явному намерению; при двух целях без приоритета — `unknown` и уточнение.
- Карточка клиента: `client_id`, цель, интересы, подтверждающая цитата, следующий шаг, `do_not_contact`, черновик сообщения наставника (`requires_human_approval = true`, автоотправка запрещена).
- Роль наставника: сверка номера телефона с БД; только наставник получает карточку обычного пользователя.
- Остановка диалога по просьбе клиента; вопросы вне базы знаний → передача наставнику.

## 1. Какую проблему мы решаем?
Первичный контакт с новым клиентом выполняется наставником вручную; цель и интересы человека при этом часто теряются, а время на обработку одного обращения не измерено. Наш помощник автоматизирует один начальный этап: задаёт уточняющие вопросы, сам структурирует ответы и формирует готовую карточку с обоснованием (цитата) и следующим шагом. Наставник получает не переписку, а заполненный контекст и черновик сообщения — и тратит время на человека, а на разбор сообщений.

Важно: автоматизируется **первый диалог**, а не вся воронка продаж. Все сообщения наставника остаются черновиками с ручным подтверждением.

## 2. Сегменты пользователей

### Новый клиент (учебные события F001–F010)
Человек, который только что зарегистрировался (в учебном стенде — событие из JSON) и ещё не общался с наставником. По явному намерению из диалога он попадает в один из четырёх учебных сегментов:

1. **Покупка для себя (`personal`)** — ищет товары для личного потребления, интересуется категориями («уход за домом»). Ценит подбор материалов без давления.
2. **Дополнительный доход (`income`)** — ищет подработку, готов уделять ограниченное время (например, «два вечера в неделю»). Чувствителен к обещаниям заработка — гарантировать их нельзя.
3. **Развитие бизнеса (`business`)** — хочет развивать свою группу, имеет опыт руководства. Ему нужна встреча с наставником и конкретные вопросы по формату.
4. **Цель не определена (`unknown`)** — «просто смотрю», нескольких целей без приоритета, или прямое «не пишите мне» (отказ от общения имеет приоритет над всеми маршрутами).

### Наставник
Владелец процесса (структура держателя кейса). Получает заполненную карточку клиента, подтверждает итоговый шаг и отвечает на вопросы вне базы знаний. Определяется по номеру телефона в БД; доступ к карточкам — только у наставников.

---

## 3. Pain Points

### Новый клиент
Ответы приходят в свободной форме, и вручную их не разложить по полям без потерь. На незаданный вопрос о цене или скидке легко получить выдуманный ответ, а обещание дохода или лечебных свойств подрывает доверие. Если цель не определена, клиенту предлагают случайный маршрут — и он отваливается на первом шаге.

**Как решают сейчас:** переписка в мессенджерах вручную, заметки в блокноте/Excel, потеря контекста между сообщениями.

### Наставник
Тратит рабочее время на первичный опрос вместо живого общения; не видит, что человек уже ответил; не знает, задан ли вопрос, на который у него нет ответа в базе. Повторная регистрация клиента создаёт дубли.

**Как решают сейчас:** ручное чтение переписки, карточки заводятся «в голове», история не сохраняется.

---

## 3.1. Анализ текущих решений

**1. Ручной первичный контакт (мессенджер/телефон)**
- Плюсы: живой тон, гибкие вопросы.
- Минусы: цель и интересы теряются; нет единого формата карточки; высокая стоимость времени наставника; нет обработки 10+ обращений параллельно.

**2. Статичная онлайн-анкета (форма на сайте)**
- Плюсы: структурированный ввод сразу по полям.
- Минусы: «всё или ничего» — непонятные ответы не уточняются; низкая доходимость до конца; не умеет работать со свободным текстом.

**3. Готовые чат-боты «по шаблону» (деревья ответов)**
- Плюсы: предсказуемость, дешёвый запуск.
- Минусы: понимают только заранее заданные фразы; нестандартный свободный ответ ломает сценарий; не извлекают цель и интересы из свободной речи.

**4. LLM-ассистент «в лоб» (без БД и правил)**
- Плюсы: свободно ведёт диалог.
- Минусы: выдумывает акции и обещания дохода; ничего не сохраняет; без контроля сегментации и отказа от общения — неприемлемо для бизнеса.

### Возможность для нас: гибрид — FSM-бот с детерминированными учебными правилами сегментации поверх LLM-извлечения свободных ответов, локальной БД и карточки-черновика с обязательным подтверждением наставником. Так закрывается и качество извлечения, и безопасность ответов, и сохранение контекста.

## UC1 — Ответить на вопрос

| Поле              | Описание |
|-------------------|----------|
| **Название**      | Ответить на вопрос |
| **Акторы**        | Пользователь, Наставник (наставник может делать то же, что пользователь) |
| **Предусловия**   | У актора есть уникальный `client_id` и доступ к боту; карточка существует или создаётся по первому входу |
| **Основной сценарий** | 1. Пользователь зашёл в бота.<br>2. Система задаёт ему вопрос через FSM (цель, интересы, доступное время).<br>3. Пользователь отвечает. |
| **Постусловия**   | Карточка с ответом сохранена в БД; карточка актуализирована (добавлены `client_id`, ответ, подтверждающая цитата, следующий шаг) |

| **Ошибки**        | E1. LLM-сервис недоступен → перебор провайдеров (OpenRouter → Mistral → Ollama), при полном отказе — сообщение об ошибке и сохранение сырого ответа в карточку.<br>E2. Пустой ввод → вежливая просьба переформулировать.<br>E3. Пользователь просит прекратить общение → `do_not_contact = true`, опрос останавливается (KB06). |

## 5. Value Proposition

«Клиент ответил свободным текстом — наставник получил готовую карточку с доказательством и следующим шагом.» Помощник проводит первый диалог по конечной машине состояний, LLM извлекает из ответов структуру (цель, интересы, числа, категории), правила сегментации не дают выдумать цель, а любой спорный вопрос уходит наставнику в виде черновика, который человек подтверждает сам. Так сохраняется каждый ответ клиента и экономится время наставника без рисков для доверия.

---

## 6. North Star Metric

Доля первичных диалогов, завершённых заполненной карточкой с явной целью (или явным отказом), которую наставник принял без доопроса клиента.

### Граница между половинами

Вопросы клиенту задаёт машина состояний, LLM-агент извлекает сведения и обновляет
карточку. `missing_information` — очередь того, что ещё спросить (по элементу на поле);
`clarifying_question` — только кандидат на реплику, не покрытую типовым вопросом FSM
(F004/F005), пустая строка в этом поле норма. Состав полей карточки — контракт между
половинами: менять только вместе.

Не сделано и относится к задаче фулстака: FSM с типовыми вопросами, сверка номера
телефона при входе, скрипт занесения тестовых клиентов и наставников в БД, колонка
состояния опроса в таблице карточки.

### Разойдённость имён переменных окружения

Таблица «Переменные окружения» выше описывает план (`TELEGRAM_BOT_TOKEN`, `DB_PATH`,
`MODEL_NAME`, `DB_INIT_ON_START`). Код в этом репозитории читает другие имена:
`BOT_TOKEN`, `DB_LITE`, `LLM_MODEL`, `LLM_TEMPERATURE`, `LLM_BASE_URL`, `LLM_API_KEY`,
`MENTOR_USER_IDS`, `DB_RESET`, `DB_ECHO`, `TEST_DELAY`. Один `.env` на два набора имён
работать не будет — перед сборкой контура нужно выбрать одну схему (правится либо в
`config.py`, либо в `common/llm.py` и `database/engine.py`).

### Как проверить

```bash
python scripts/check_llm.py prompt              # собранный системный промпт
python scripts/check_llm.py test F002           # карточка по учебному событию
python scripts/run_tests.py                     # F001–F010 из tests.json
python scripts/run_paraphrases.py               # 21 перефразированный вход
```

Итог последнего прогона на `qwen2.5:7b-instruct` (temperature 0.3): 10/10 PASS по
базовым кейсам и 21/21 PASS по перефразам, дважды подряд — лог в
`_baseline_qwen25_7b_t03.txt`. Эти прогоны проверяют только агента: накопление
карточки через FSM, остановка контакта и доступ наставника проверяются на собранном
конуре (F011, F012).


### Готово: половина фулстака в `bot_fullstack/` (ветка `qoder/bot-fullstack`)

Закрывает пункты «не сделано» из раздела выше: FSM с типовыми вопросами, сверка
номера телефона при входе, занесение тестовых клиентов и наставников в БД, колонка
состояния опроса в карточке. Отличие от основного контура: выводы считает
детерминированный движок учебных правил (`bot_fullstack/assistant/engine.py`), без
обращения к LLM — поэтому прогоны воспроизводимы и не требуют ни токена, ни Ollama.
Учебные данные читаются из общего `data/fb01/`.

Запуск и проверка (из корня репозитория):

```bash
cd bot_fullstack
pip install -r requirements.txt
python scripts/run_tests.py       # 97 проверок: движок, загрузчик F011/F012, сверка телефона, доступ
python scripts/bot_flow_test.py   # 31 шаг живого диалога через настоящий диспетчер
```

Отчёт с фактическими значениями и временем — `bot_fullstack/results/FB01_проверки.md`.

Что нужно решить при слиянии:

- доступ наставника здесь держится на **номере телефона** (`.env`: `MENTOR_PHONE`),
  а не на `MENTOR_USER_IDS`; в таблице `mentor` есть `phone` (уникальный) и
  `telegram_id`, который подставляется после того, как человек прислал свой номер;
- имена переменных окружения расходятся с текущим контуром (`TOKEN` против
  `BOT_TOKEN`, `DB_URL` против `DB_LITE`) — при сборке выбираем одну схему;
- поля карточки: здесь `segment`, `goals`, `interests`, `available_time`,
  `experience`, `flags`, `do_not_contact`, `open_question`, `dialogue_step`.
