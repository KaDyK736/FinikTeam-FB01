# FB01 — ИИ-помощник нового клиента (учебный прототип)

Telegram-бот на aiogram 3 + SQLAlchemy 2 (async) + SQLite, который ведёт
первичный диалог с новым клиентом: сверяет номер с базой сайта, определяет
сегмент цели, собирает недостающие параметры, формирует карточку и черновик
сообщения наставнику.

Это часть контура команды Finik за авторством Веденеева В. С. (Fullstack):
бот, локальная база, FSM и роль наставника. Отличие от основного контура
репозитория — выводы делает детерминированный движок правил
(`assistant/engine.py`), без обращения к LLM, поэтому прогоны воспроизводимы
и не требуют токена. Код живёт в папке `bot_fullstack/`, учебные данные берутся
из общего `data/fb01/` репозитория (рядом можно положить и `02_Учебные_данные/`).

Прототип учебный: все данные вымышлены, держатель кейса — Faberlic, пожелание —
общение через мессенджер MAX (план подключения ниже).

## Что делает помощник

1. **Сверка с сайтом.** При входе бот просит номер телефона (кнопкой или текстом)
   и ищет его в выгрузке анкеты регистрации. Если анкета с сайта есть —
   дополняет карточку полями формы (город, ФИО, пол, e-mail, дата рождения,
   телефон пригласившего) и **не заводит дубль**. Если номера нет — создаёт
   карточку `B<telegram_id>` и помечает, что данные пришли из диалога.
   Можно вместо номера написать идентификатор события (`F002`).
2. **Доступ наставника — по номеру телефона.** Номера наставников перечислены в
   `database/site_export.py` (`MENTOR_PROFILES`) и в `.env` (`MENTOR_PHONE`,
   через запятую). Когда человек присылает такой номер, карточка клиента **не
   заводится**: бот привязывает к записи наставника идентификатор его чата и
   открывает `/cards`. До сверки номера доступа нет — `MENTOR_TG_ID` больше не
   используется. Номер наставника важнее анкеты клиента: одно и то же число не
   может быть одновременно наставником и клиентом.
3. **Первичный диалог (FSM).** Вопросы следуют из базы знаний: цель знакомства →
   при двух целях без приоритета одно уточнение → интересующие категории →
   доступное время (для дохода) или опыт работы с людьми (для бизнеса).
   Известное не переспрашивается.
4. **Карточка** в формате `output_example.json`: сегмент, цитата-доказательство,
   интересы, чего не хватает, `do_not_contact`, `next_action`, `draft_message`,
   `requires_human_approval: true`.
5. **Правка параметров, которых нет на форме сайта** — кнопка «Изменить анкету»:
   цель, интересы, доступное время, опыт, согласие на обращения. Поля самой
   формы регистрации (ФИО, город, e-mail, телефон, дата рождения, пригласивший)
   бот показывает только для чтения: их меняет сайт. Прежнее значение остаётся
   в истории карточки, сегмент и следующий шаг пересчитываются.
6. **Красные флаги.** Акций, цен и условий доставки в учебном наборе нет — бот их
   не выдумывает (KB04); доход и лечебные свойства не обещает (KB08);
   регистрацию и оплату за человека не выполняет (KB05); просьбу «не писать»
   исполняет сразу и полностью (KB06). Все спорные вопросы — черновик наставнику.

## Структура

```
app.py                  сборка диспетчера (aiogram 3, Router + FSM + middlewares)
assistant/engine.py     правила: сегменты, интересы, флаги, следующий шаг, черновик
assistant/knowledge.py  чтение учебных данных кейса
database/models.py      Client (поля сайта + поля диалога), DialogueTurn, Mentor
database/repository.py  загрузка событий, сверка телефона, правки, история
database/site_export.py заглушка выгрузки анкеты с сайта + номера наставников
handlers/               client_private.py (диалог и правки), mentor.py, admin.py
states/, kbds/, filters/, middlewares/, utils/, common/  — слои курса Python Hub Studio
scripts/run_tests.py    12 проверок tests.json + границы прототипа
scripts/bot_flow_test.py сквозной прогон настоящего диспетчера без токена
scripts/console_chat.py тестовый интерфейс диалога в консоли
results/                отчёт прогона с фактическими значениями и временем
```

## Запуск

```bash
cd bot_fullstack                # все команды — из этой папки
pip install -r requirements.txt
cp .env.example .env            # в .env кладётся токен от @BotFather и MENTOR_PHONE
python app.py                   # база поднимется и сама нальёт события регистрации
```

Наставнику достаточно один раз прислать боту свой номер из `MENTOR_PHONE` —
дальше доступ держится за ним. Старая локальная база с таблицей наставников
прежнего вида не ломается: при старте пересоздаётся только таблица `mentor`
(это конфиг, а не данные клиентов), привязка чата восстановится по номеру.

Проверки (токен не нужен):

```bash
python scripts/run_tests.py       # 97 проверок движка, загрузчика, сверки телефона и доступа
python scripts/bot_flow_test.py   # 31 шаг живого диалога через диспетчер
python scripts/console_chat.py    # тот же диалог в консоли
```

Сценарий, который удобно посмотреть первым: `python scripts/bot_flow_test.py` —
он прогоняет настоящий диспетчер без токена: вход клиента по номеру, вопрос про
цель, правка параметра, которого нет на форме сайта, отказ от общения, затем вход
наставника по его номеру и `/card F002` с черновиком `requires_human_approval`.
Отчёт с фактическими значениями и временем прогона лежит в `results/`.

Команды бота: клиенту — `/start`, `/cancel`; наставнику (его номер телефона есть
в списке наставников) — `/cards`, `/card F002`; администратору (`ADMIN_TG_ID`) —
`/load`, `/event {json}`, `/stats`.

## Как проверялось

Ожидаемые ответы из `tests.json` сравнивает прогонщик `scripts/run_tests.py` —
в правила агента они не попадают (файл читает только тестовый бегунок).
Фиксируются id проверки, фактические значения, время прогона; результат —
в `results/FB01_проверки.md`. Проверен смысл вывода, а не дословный текст:
сегмент, `do_not_contact`, `next_action`, наличие цитаты-доказательства,
`requires_human_approval`, отсутствие выдуманных условий.

Две дополнительные самопроверки из описания кейса:

- перефразированный запрос без явной цели («Просто интересуюсь, что это вообще за
  возможности.») → сегмент `unknown`, уточняющий вопрос, цель не угадывается;
- смена входного параметра («Хочу покупать для себя» → «Скорее развивать
  команду») → сегмент `personal` → `business`, следующий шаг пересчитан,
  прежняя формулировка осталась в истории;
- доступ наставника: номер из списка наставников открывает `/cards` и не
  заводит карточку клиента, а до сверки номера доступа нет — ни по какому
  `telegram_id` (проверки «наставники заведены по номеру телефона»,
  «номер наставника не заводит карточку клиента», «чужой номер остаётся
  клиентом» в отчёте и шаги «наставник опознан по номеру телефона»,
  «карточка клиента для наставника не заведена» в сквозном прогоне).

## Границы и безопасность

- Прототип не выполняет внешних действий: ничего не регистрирует, не оплачивает,
  не заходит в личный кабинет, не отправляет сообщения от имени человека.
- Все сообщения наставнику — черновики с `requires_human_approval: true`.
- Паспортных, банковских данных и паролей бот не запрашивает (KB08).
- Телефон наставнику показывается скрыто (`+7904 *** ** 80`), карточка
  идентифицируется по `client_id`.
- Право на карточки даёт номер телефона из списка наставников, а не
  идентификатор чата: знать чужой `telegram_id` для доступа недостаточно.
  Реальные номера наставников лежат только в `.env` (не в архиве).
- Учебный набор синтетический. Реальные или обезличенные данные держателя
  кейса не использовались; условия их передачи внешним ИИ-сервисам нужно
  уточнять до работы с ними.

### Перед публикацией архива удалить

1. `.env` (токен и реальные номера наставников из `MENTOR_PHONE`) — в
   репозиторий не попадает, он в `.gitignore`.
2. `database/site_export.py` — все записи вымышленные; если добавите свой
   настоящий номер для проверки сверки, уберите его в `.env` (`MENTOR_PHONE`),
   а не в код: реальные персональные данные в кейсе запрещены.
3. Локальные базы `*.db` (`fb01_bot.db`, старый `mentors_bot.db`) — там реальные
   данные тестового чата.

## Мессенджер MAX: план подключения

Держатель просит общаться с клиентом через MAX. Подключения к MAX в учебном
стенде нет, поэтому диалог показан в Telegram-боте и в консольном интерфейсе —
на одном и том же движке правил. Чтобы перенести его в MAX:

1. Получить у держателя требования интеграции: API/вебхук, формат идентификатора
   пользователя, правила маркировки сообщений.
2. Вынести отправку сообщений из хендлеров в адаптер `ChannelAdapter`
   (`send`, `edit`, `callback`) — сейчас это `aiogram.Bot`.
3. Реализовать `MaxAdapter`: приём входящих сообщений → нормализация в тот же
   формат «текст/телефон», отправка ответов, обработка нажатий кнопок.
4. Канал привязки клиента: в MAX нет Telegram-`user_id`, поэтому ключом
   сверки остаётся телефон (или `client_id` из события сайта) —
   `orm_link_phone` и `orm_link_client_id` уже работают по этим ключам.
5. FSM и хранилище состояний перенести с `MemoryStorage` на постоянную базу
   (например та же SQLite-таблица), чтобы диалог пережил перезапуск и работал
   из двух каналов одновременно.
6. Один клиент в двух каналах: карточка общая, история реплик помечается
   каналом (`DialogueTurn`), повторные вопросы не дублируются — `next_question`
   уже не спрашивает известное.
7. Тестовый стенд: прогнать `scripts/run_tests.py` против `MaxAdapter` — движок
   от канала не зависит, поэтому ожидаемые результаты совпадут.
